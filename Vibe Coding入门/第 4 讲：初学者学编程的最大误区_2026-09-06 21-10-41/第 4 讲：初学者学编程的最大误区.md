## 一、开篇：同一个 AI，两种命运

先给你讲两个真实的使用场景。

**场景 A：** 小李下载了 AI 工具，虔诚地敲下："请教我学编程。"AI 给出了一份从变量、循环讲起的学习路径。小李跟着学了三天，每天两小时，笔记记了十几页。第四天，工作一忙，断了。第五天，看着笔记觉得陌生。第七天，卸载。结论："编程太难了，我不是这块料。"

**场景 B：** 小王下载了同一个工具，敲下："帮我做一个部门聚餐的投票页面，五个选项，大家点一下就能投票，实时显示票数。"十分钟后，页面做好了，发到部门群里，当晚 23 个人投了票。小王又花了二十分钟，让 AI 把配色改成了公司 VI 的颜色。结论："这玩意真香，明天再做一个。"

三个月后，小李对 AI 编程的认知还停留在"学过一点变量"；小王已经做出了六个工具，成了公司里"那个会做东西的人"。

**同一个工具，差距在哪？** 不在智商，不在基础，在于进门第一天，他们和 AI 建立的关系完全不同：

**小李把 AI 当老师，小王把 AI 当员工。**

这一讲，就是要把"当员工"这个心法给你讲透、装稳。因为它将决定你后面每一次打开 AI 时的姿势。

## 二、为什么"把 AI 当老师"是个坑

### 2.1 学生模式的三宗罪

**第一宗：慢。** 传统学法从概念讲起，变量、数据类型、循环、函数……学到能做出一个像样页面的程度，正常要两三个月。而成年人的学习，超过两周没有正反馈，放弃率超过 80%。你不是学不会，你是等不到甜头。

**第二宗：错位。** 你学编程的目的是"做出东西"，不是"成为程序员"。但学生模式默认你要走职业路线，给你塞大量"以后可能有用"的知识——就像你想学做三道家常菜，老师非让你先读《烹饪化学原理》。

**第三宗：消耗信心。** 概念听不懂 → 觉得自己笨 → 更不敢动手 → 更做不出东西 → 确认"我不行"。这是一个教科书级的负循环，而且它完全是人为的——你本来可以绕过整个环节。

### 2.2 一个扎心的对比

传统学法和 Vibe Coding 学法的目标差异：

|     |     |     |
| --- | --- | --- |
|     | 传统学法 | Vibe Coding 学法 |
| 目标  | 学会编程 | 做出东西 |
| 路径  | 概念 → 练习 → 项目 | 项目 → 在做中补概念 |
| 第一个作品 | 第 2-3 个月 | 第 1 天 |
| 代码由谁写 | 你   | AI  |
| 你的角色 | 学生  | 老板  |

看清楚：**你不是来上学的，你是来当老板的。**

## 三、"把 AI 当员工"的正确姿势

### 3.1 重新定义你和 AI 的关系

想象你刚招了一个实习生。这个实习生的画像是：

-   **执行力爆表**：你说做什么，他秒做，不拖延不抱怨；

-   **知识量爆表**：全世界的代码他都会写；

-   **但对你的业务一无所知**：他不知道你是干嘛的、给谁用、为什么急；

-   **而且没有主见**：你说清楚，他做到 120 分；你说不清楚，他只能瞎猜，猜错他也不觉得是自己的问题。
    

现在请问：怎么用好这个实习生？答案每个带过人都懂——**活要派清楚，结果要验收，不满意要说清哪里不满意。**

这就是"把 AI 当员工"的全部内涵。它对应三个具体动作：\*\*派活、验收、反馈。\*\*下面逐个拆。

### 3.2 动作一：派活——把需求说清楚

差劲的派活："做个表单。"

合格的派活："做个课程报名表单，给 30-50 岁企业管理者在手机上填。字段：姓名、手机号（要校验 11 位）、公司、职务。风格商务克制，白底藏蓝标题。提交按钮写'锁定席位'，提交后显示'报名成功，1 个工作日内短信通知'。"

差距在哪？合格的派活包含四个要素：

|     |     |     |
| --- | --- | --- |
| 要素  | 回答的问题 | 示例碎片 |
| 做什么 | 交付物是什么 | "一个报名页面" |
| 给谁用 | 用户是谁、什么场景 | "30-50 岁管理者，手机扫码填" |
| 必须怎样 | 硬约束 | "手机号必须校验""白底" |
| 不能怎样 | 雷区  | "不要花哨动画" |

**自检口诀：派活之前问自己——这段话发给一个聪明但不知情的外包，他能做对吗？**（第 22 讲会把这个口诀升级成完整公式。）

### 3.3 动作二：验收——看结果，不看过程

小白的常见纠结："AI 写的代码我看不懂，心里没底。"

请回忆一下：你给设计师派了个海报活，收到稿子后，你会要求设计师"把 PSD 的每个图层讲给我听"吗？不会。你看的是：整体美不美、信息全不全、品牌色对不对、有没有错别字。

\*\*验收 AI 的代码，和验收设计师的海报，一模一样。\*\*你的验收清单只有四项：

1.  **能打开吗？** 双击文件，浏览器正常显示，不空白不报错；

1.  **是我要的格局吗？** 该有的板块都有，顺序对；

1.  **是我要的感觉吗？** 风格、配色、文案对味；

1.  **功能灵吗？** 每个按钮、输入框都点一遍，结果符合预期。
    

四项全过 = 合格交付，收下。哪项不过 = 进入下一个动作：反馈。

### 3.4 动作三：反馈——说清哪里不满意

最没用的反馈："不好看。""不太对。""再改改。"

AI 收到这种反馈，和你收到甲方这种反馈时的心情一模一样：想死，而且只能瞎改。

\*\*有效的反馈 = 指位置 + 说现状 + 给方向。\*\*对比感受一下：

|     |     |
| --- | --- |
| 无效反馈 | 有效反馈 |
| "不好看" | "标题颜色太浅了，换成深藏蓝，字号再大一号" |
| "不好用" | "我点了提交按钮没反应，手机号填错也没有提示" |
| "太乱了" | "三个板块挤在一起，每个板块之间加 40px 间距，再加一条浅灰分割线" |

发现了吗？有效反馈根本不需要技术词汇——**位置、颜色、大小、间距、文案、现象**，全是日常语言。你审了十几年稿、改了十几年方案的那套"提意见"的肌肉，直接平移过来就是满分水平。

### 3.5 话术库：验收后的四种标准动作

把 AI 当员工，日常只需要四种对话，直接抄：

**① 全部满意，进入下一步：**

> "这版可以。下一步，帮我在页面底部加一个'常见问题'板块，三个问题，用折叠面板的形式。"

**② 局部修改：**

> "整体可以，只改一处：把提交按钮的文案从'提交'改成'马上锁定席位'，按钮颜色换成藏蓝，其他一律不动。"

**③ 出了 bug：**

> "出问题了：我做了【双击打开 index.html】，期待看到【蓝色报名页】，但实际【页面空白，控制台报错如下】。帮我定位原因并修复，其他功能不要动。"

**④ 推倒重来（局部）：**

> "中间的'课程介绍'板块方向不对，删掉重做：改成左右结构，左边课程海报图（先用占位图），右边三段介绍文字。其他板块保持不变。"

注意 ②③④ 里反复出现的那句话——**"其他一律不动"。** 这是防止 AI"顺手优化"把你满意的部分也改坏的紧箍咒，务必养成习惯。

## 四、两个需要破除的担心

**担心一："不问原理，万一 AI 骗我/写错了怎么办？"**

你的质检不是靠"看得懂"，是靠"验得出"。功能对不对，点一下就知道；效果好不好，看一眼就知道。结果不会骗你。至于原理——等你做出三个作品、好奇心真正被勾起来之后，再问"刚才那是怎么实现的"，AI 会高兴地给你讲一节课。先做出来，再懂原理，顺序不能反。

**担心二："我一直当'伸手党'，会不会永远没长进？"**

恰恰相反。你每提一次需求、每验一次收、每给一次反馈，都在积累"产品感觉"——什么结构合理、什么交互顺手、什么文案有效。三个月后再看，你聊产品的专业度会吓自己一跳。**长进不在代码里，在判断力里。**

## 五、动手做（本讲作业，重要）

**任务：用"员工模式"重写你的需求。**

1.  找出第 1 讲写下的"我想做的一个小东西"的原始描述；

1.  用今天学的四要素（做什么/给谁用/必须怎样/不能怎样）重写它，写成一段可以直接发给 AI 的"派活需求"；

1.  对照自检清单检查。
    

**改写示例（找感觉）：**

原始描述："我想要一个记录读书的工具。"

员工模式改写：

> 【做什么】帮我写一个 HTML 文件：个人阅读记录工具。
> 
> 【给谁用】我自己用，主要在电脑浏览器上，偶尔手机查看。
> 
> 【必须怎样】① 输入书名和今天读的页数，点保存，加入记录列表；② 页面顶部显示"本月已读 X 页、连续 X 天"；③ 数据刷新后不丢失（用 localStorage 保存）；④ 风格：深色背景、暖黄灯光感，像深夜书房。
> 
> 【不能怎样】不要登录注册，不要任何广告位。

**自检清单：**

-   \[ \] 包含了全部四个要素？

-   \[ \] 每句话都是一个不知情的人也能看懂的白话？

-   \[ \] "不能怎样"里写了至少一条明确雷区？

-   \[ \] 写完后我自己读一遍，觉得"照这个做，做出来就是我想要的"？
    

这份需求请收好——**第 19 讲，它就是你的实战题。**

## 六、常见坑（FAQ）

**Q1："我对 AI 说话需要礼貌吗？要说'请'和'谢谢'吗？"**

随你心情。礼貌不会让结果更好，粗暴也不会让结果更差——但**清晰会**。把斟酌语气的精力省下来，多写一句具体约束。

**Q2："AI 给的结果和我预期差很远，是它不行吗？"**

先别急着怪员工。用四要素检查你的派活：是不是少了背景？约束没说？十有八九，是需求给薄了。员工再强，也做不出你没说的需求。

**Q3："我可以一口气提十个要求吗？"**

派新活时可以（需求越完整越好）；**改旧活时不行**。修改要"一次一处"，这是第 24 讲的铁律，先记住。

**Q4："感觉自己像个'伸手党'，有点虚。"**

产品经理也是"伸手党"——他们不写代码，但决定产品做什么样。你现在的角色就是"自己作品的产品经理"。把需求想清楚、把验收做到位，就是你的核心价值，一点都不虚。

## 七、本讲小结

1.  \*\*把 AI 当员工，不当老师。\*\*你是来定目标、做验收、给反馈的老板，不是来背概念的学生。

1.  **三个标准动作：派活（四要素说清）、验收（看结果不看过程）、反馈（指位置+说现状+给方向）。**

1.  **紧箍咒：任何修改，末尾加一句"其他一律不动"。**

1.  你的长进不在代码里，在判断力里——而判断力，你本来就有底子。
    

**下讲预告：** 关系理顺了，还有最后一道心法防线要建：怎么面对"做出来的东西不够好"这件事。第 5 讲送你第一条军规——先做出丑东西，再做出好东西。这条军规能救你免于 90% 的中途放弃。
